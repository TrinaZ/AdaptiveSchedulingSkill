## Motivation

All earlier results use a synthetic genomics workload. The assessment and the independent review both identified external validity as the main risk. H8 asks whether the governance results and the LLM-value results carry over to real request streams.

## Workload

Real tasks from `batch_task.csv` (status Terminated): real arrival times, real durations and real CPU requests. Two 12-hour windows were chosen automatically as the busiest windows at least 2 days apart (see the extraction log).

| Aspect | Setting |
|---|---|
| Scenes | **T0** and **T1**: the two windows at natural load (capacity set so the average offered load is 1). **T0cap** and **T1cap**: the same windows with 30% less capacity. |
| Instances | 60 consecutive real tasks each |
| Search instances | first 20% of a window |
| Validation instances | 20–60% of a window |
| Held-out instances | last 40% of a window, so the rule is deployed on the *future* |
| Synthesised fields | Runtime estimate (×U[0.6,1.4]), due time, tenant (20% of *jobs* are premium) and weight, all exactly as in the main benchmark |

## Hypotheses

**H8a (governance, confirmatory).** For each of knowledge_tuned, llm_skill and llm_skill@ds-reasoner:
- the gated violation rate (paired t gate) is ≤ 5%; and
- ungated violations exceed gated violations, by an exact McNemar test, one-sided, α = 0.05.

**H8b (standard LLM).** llm_skill vs knowledge_tuned, two-sided Wilcoxon on rel.
- Our prediction from H6 is *no difference*.
- This is reported as an estimate, not as a test we expect to reject.

**H8c (reasoning model, confirmatory).** llm_skill@ds-reasoner < knowledge_tuned, one-sided Wilcoxon on rel, α = 0.05. This replicates H6′ on real traffic.

**Reported without a claim.** gp100, pool_full, and the per-objective breakdown.

## Reporting

- **All outcomes are reported.**
- **If H8a fails,** the paper states that the gate's guarantee did not carry over to real traffic. The likely cause is non-stationarity inside a window, which violates G2; the paper says so, and that becomes a main finding.
- **No scene, objective or window is changed after the first LLM call.**

## Amendment 1: runtime guard (2026-10-17 16:25, UTC+8)

**What happened.** At 16:09 the 10 LLM runs started. Two of them, deepseek-chat and deepseek-reasoner on `slo_wait`, crashed within minutes with `TypeError: '>' not supported between 'NoneType' and 'float'`.

**Cause.** A selected rule raised an exception on held-out traffic. The most likely source is `math.exp` overflow: queueing delays in the trace reach thousands of seconds, far above the synthetic workload's scale. The frozen benchmark had no branch for this case, because it never happened on the synthetic workload.

**Fix (in `make_trace_bench.py`, substitution 5).**
- If the selected rule raises on held-out traffic, it is replaced at run time by the search-selected library rule, as a runtime guard in a deployed dispatcher would do.
- That deployment is counted as a **violation**, both ungated and gated.
- Each record gets `heldout_error`.

**Scope.**
- The deepseek-chat runs for tard, miss, mix and premium had already finished without any runtime error. Their records are identical under the amendment and are kept (`h8_analysis.py` reports `heldout_error` counts).
- The other six runs were restarted with the amended file: deepseek-chat on slo_wait, and deepseek-reasoner on all five objectives.
- No result had been inspected when the amendment was made. Nothing else changed.
